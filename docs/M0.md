# M0 — Technology Prototype

## Objective

Prove the smallest version of the competitive loop before investing in MMO meta, monetization or large-scale infrastructure.

## Scope

### Core

- Unity mobile input prototype.
- One shared board.
- Identical letter set for both players.
- Server-authoritative 1v1 match.
- Word validation against a versioned dictionary.
- Claim, 3-second lock and Cross-Steal state transitions.
- Deterministic scoring and combo calculation.
- Client prediction with rollback.
- Reconnect/resume during an active match.
- Network simulation for latency, jitter, packet loss and reordering.

### Explicitly out of scope

- 60-player Word Royale.
- Guilds and territory.
- World bosses.
- Battle pass and store.
- Full GIS anti-cheat scoring.
- Multi-region production cluster.
- WebGL/PC client.

## M0 acceptance tests

A prototype is considered complete only when all are reproducibly demonstrated:

1. Two clients receive the same deterministic board seed.
2. Simultaneous claims resolve identically for both clients.
3. A rejected or lost prediction converges to the server snapshot without a scene reload.
4. A client disconnected for less than the configured grace period can resume.
5. The same match event log produces the same final score when replayed.
6. The dictionary validator returns identical results on all supported development platforms.
7. Tests pass under simulated RTT 50/100/150 ms and loss 0/1/3%.
8. A load test establishes a measured baseline for actions per second and server CPU/memory per active match.

## Performance gates

The initial targets are engineering hypotheses, not sacred numbers. Record measured p50/p95/p99 values in benchmarks and revise targets from evidence.

- Match simulation: stable 30 Hz tick.
- Word validation: benchmark in-process lookup, not end-to-end request latency.
- Input acknowledgement: establish p95/p99 separately from game-state replication.
- Client frame rate: 60 FPS target on the baseline device class.
- Reconnect: canonical snapshot accepted without scene reload.

## Required test assets

```text
tests/
├── fixtures/              # deterministic board, dictionary and match fixtures
├── network/               # latency/loss/reordering profiles
├── golden/                # expected scoring/state transitions
└── load/                  # synthetic clients and action distributions
```

## First architectural decision

Keep the authoritative simulation in one language and one process model for M0. Do not split match logic across Go/Rust/C++ until a measured bottleneck exists. Every extra boundary is another place for a desync to breed.
